# Richer metadata fields

**Songs**: writing credits and year remain the only structured metadata beyond title. A writing credit targets an Artist and retains its `composer`, `lyricist`, or generic `writer` role; do not reduce the model to person-only composer/lyricist columns. Year means year written ([ADR-0007](../adr/0007-original-dates-and-albums.md)); MusicBrainz sourcing is best-effort and commonly null because writing relationships often lack dates. A "part of" text field (e.g. *Show Boat*) is planned — see [musicbrainz-matching.md](musicbrainz-matching.md).

**Recordings**: [ADR-0008](../adr/0008-provider-neutral-music-entities-and-user-data.md) defines Recording as canonical and provider-neutral. Shared fields live on `recordings`; private saved state lives on `user_recording_data`. `kind` (`released` / `video_capture`) was the first decided field. Do not add `user_upload` to that enum merely to represent a future self-hosted source: source and release status are separate dimensions, and the status term for an unreleased audio-only/home recording is still undecided. Shared `album`, `year`, and `duration` remain plain columns (free text/simple types, no controlled vocabulary); the legacy `artist` column transitions to Attribution Fallback text:

- `duration` may initialize from selected YouTube evidence but stays editable. A YouTube Music artist name or ordinary YouTube channel can initialize Attribution Fallback text, but provider wording does not create a canonical Artist automatically. Provider album identity remains on `youtube_items` rather than being copied into the canonical album hint.
- `recording_date_start` / `recording_date_end` hold true partial-precision performance dates from Recording-to-Work relationships. YouTube release/album metadata, `first-release-date`, and legacy `year` are never performance-date evidence. Legacy `year` remains only for compatibility with unmatched/manual rows.
- `release_group_id` points to the shared master-level display context. `album` remains an editable compatibility hint for unmatched/manual rows, and the stored MusicBrainz Release MBID is only a representative edition for source/detail and artwork fallback; see [musicbrainz-matching.md](musicbrainz-matching.md).
- Recording Attribution is an ordered structured list of Artist references, credited-as names, and exact following join phrases, not a replacement for structured Personnel. MusicBrainz may supply several credited Artists plus arbitrary join phrases; Standards preserves those parts rather than forcing an ampersand. Attribution is genuinely distinct from Personnel (e.g. Barney Kessel playing guitar on a Billie Holiday recording). Render structured Attribution first, then Attribution Fallback, then a selected provider hint, then the Recording descriptor. Preserve the fallback when structured Attribution is added so legacy and unmatched values can be audited before any later removal.
- Store Recording Attribution parts in an explicit Recording-to-Artist relationship and Release Group Attribution parts in a separate explicit Release Group-to-Artist relationship. Both use the same shape—credited-as name, exact following join phrase, and sort order—and share validators, normalization, formatting, and editor behavior; do not introduce a polymorphic subject ID.
- Manual Attribution editing searches and reuses an existing canonical Artist or explicitly creates a provider-unmatched Artist when none matches. Credited-as text defaults from the selected or typed name but remains independently editable, as does the exact following join phrase. Never split or link Attribution Fallback automatically. Once structured Attribution exists, hide fallback from normal presentation but retain it as unresolved text in the editor until the User deliberately clears it.
- Provider imports preserve the complete ordered credit sequence exactly, including repeated references to the same Artist, distinct credited-as variants, punctuation, and whitespace in every join phrase. Do not deduplicate or cosmetically normalize provider credits; decoding transport escaping and enforcing bounded payload validation are not credit cleanup. Manual changes remain intentional edits.
- Recording detail presents structured personnel relationships read-only under **Personnel** immediately below the editable structured Attribution, one linked credited-as Artist name per row with that Artist's mapped relationship details grouped on the same row. A generic performer with no specific detail appears as the Artist name alone, and the entire section is omitted when no structured credits exist. Within a row, instrument details sort alphabetically, followed by vocal details, conductor, and orchestra; credited-as detail text displays when available. Personnel Artists also present in the Attribution lead the list in Attribution order; an attributed group precedes an overlapping namesake person, and all unmatched credits sort alphabetically. Attribution ordering only orders independently evidenced Personnel — it never creates a Personnel credit or infers group membership. Confirming or refreshing a MusicBrainz match updates this read-only draft preview immediately, but only the existing Recording Save action persists it; Personnel has no separate edit, reorder, delete, or refresh controls.
- `notes`, `rating`, `sort_order`, preferred playing `key`, practice `tempo`, and personal organization such as `tags` live in `user_recording_data`; canonical performance facts remain on Recording. Do not reinterpret key or tempo as measured canonical performance metadata.
- A selected YouTube/YouTube Music result retains its normalized provider snapshot in `youtube_items` and associates that item with the Recording; this includes accumulated source provenance plus nullable YouTube Music artist/album identities that cannot reliably be recovered from video-ID lookup. See [streaming-platform-links.md](streaming-platform-links.md).
- The free-text `name` field is unaffected by any of this — it is still the Recording's own title/descriptor, separate from Attribution and Attribution Fallback.

**Release Groups**: a Release Group has its own shared, editable Attribution,
separate from every contained Recording's Attribution and from any one
representative edition's artist credit. Model it as an ordered list of Artist
references with a credited-as name and following join phrase for each item;
derive the linked display text rather than storing links or character offsets
inside one string. Every part references a canonical local Artist; manual
Attribution may create or reuse an Artist without requiring a provider ID
rather than falling back to an unlinked text part. MusicBrainz can initialize or refresh this structured
Attribution, but it remains provider-neutral canonical metadata and Save—not a
background lookup—persists the draft. The first UI slice shows it with the
Release Group title in Recording detail and in the MusicBrainz match/refresh
preview. Compact Recording rows and the player remain out of scope for that
slice. Because the editor is reached through one Recording while changing a
shared Release Group, label it clearly as **Album credit — shared across
recordings**; the current trusted-development stage does not require a repeated
confirmation modal.
